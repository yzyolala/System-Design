# 09. 日志、指标与自动化：面试题与答案

## 面试真题

### Meta：设计广告点击聚合系统 / Design an Ad Click Aggregator

**答案：**

我先问按广告、时间窗口或地域聚合哪些指标，以及准确度、迟到容忍和查询延迟。接收端为事件携带 event_id、ad_id、event_time 等字段，将事件可靠写入分区日志；消费者按窗口聚合，原始事件保留用于重放和对账。

重复事件按稳定 ID 在明确的保留窗口内去重，迟到事件按 watermark 与修正规则处理，不能把接收时间默认当事件发生时间。热门广告可加盐分散局部聚合，再汇总到广告级结果。消费者进度、状态更新与重放语义要协调，避免重复计数；查询走聚合存储和缓存，监控积压、数据新鲜度和对账误差。

例如按分钟聚合时，12:01 到达但发生于 12:00 的点击属于事件时间窗口。系统要定义窗口何时关闭、迟到后是否修正，以及查询显示的是暂定还是最终结果。准确计费与近实时看板可以有不同的新鲜度和校验要求。

[题目来源](https://www.reddit.com/r/leetcode/comments/1lvnd0t/)

### Meta：设计 LeetCode / Design LeetCode

**答案：**

先确认题目浏览、提交判题、结果查询、比赛和排行榜的范围。API 保存 submission_id、用户、题目、代码引用、语言和状态，再可靠发布判题任务，返回 pending。worker 在隔离沙箱内编译运行，用 CPU、内存、时间和网络限制保护平台，测试数据也需受保护。

判题结果持久化后更新提交状态，同一 submission_id 的重复执行不能重复修改成绩。队列按语言或资源类型分组，扩容受沙箱启动和下游容量约束。比赛排名从可信结果与规则计算，缓存或增量更新读模型；监控等待时间、判题失败、热点比赛和重复消息。仅加入 MQ 不足以完成代码隔离与比赛正确性设计。

比赛题目、测试数据和用户代码要分别设权限。超时、编译错误、答案错误与平台内部失败是不同结果，平台故障可以重试，用户代码错误通常直接返回。重复任务的完成状态使用条件更新，避免晚到结果覆盖已经确认的成绩。

[题目来源](https://www.reddit.com/r/leetcode/comments/1lvnd0t/)

## 本节练习题

### Q1. 平均延迟正常，但用户反馈很慢，你看什么？

是否某个区域、接口或版本受到影响？

**答案：**

平均延迟正常并不能排除一部分请求极慢。我先检查 P95/P99、超时、失败率和真实用户侧耗时，再按接口、区域、版本、客户群和请求大小拆分，定位是否是局部问题。

随后从慢请求 trace 看连接、排队、数据库、缓存和下游时间。全局分位数要从可合并的分布计算，不能直接平均各实例 P99；平均值反映中心趋势，尾延迟反映最慢一批请求，两者都要观察。[Prometheus 官方参考](https://prometheus.io/docs/practices/histograms/)。

例如 99% 请求耗时 50 ms、1% 耗时 5 秒，平均值仍可能让问题显得不突出。慢请求若集中在某个区域或大对象下载，需要看该分组的分布，不能只看所有请求混合的一个数字。

### Q2. 一个请求经过多个服务，如何排查失败？

日志与指标分别提供什么证据？

**答案：**

入口生成或验证 trace ID，并在同步调用与异步消息中传递上下文，各服务记录 span、状态和耗时。日志结构化记录 trace ID、服务、版本、区域及错误信息，集中检索时就能关联一次请求的多个阶段。

指标先判断影响范围，trace 找到哪个调用或排队阶段耗时，日志解释具体异常。采样可控制成本，但要考虑保留错误和慢请求；不要将 user_id 等高基数字段随意放进指标标签，也不要在日志中记录敏感凭证。

异步 worker 的执行不是原 HTTP 请求持续阻塞，但仍应关联同一个任务 ID。排查“上传后迟迟没结果”时，需把上传、排队和处理三个阶段连起来，不能仅查看上传 API 的成功日志。

### Q3. 如何决定 Web 和 worker 的扩缩容指标？

只看 CPU 有什么问题？

**答案：**

对 Web 实例，我会看每实例吞吐、并发、延迟、CPU 和连接数；CPU 低但下游等待高时，加实例未必有帮助。对 worker，我更关注最老任务等待时间、入队速率和每实例处理能力。

例如生产每秒 1000 个任务、单 worker 稳定处理 100 个，理论最低是 10 个；实际还需峰值、故障和排空积压的余量。扩容要受下游容量约束，并设启动预热、扩缩容稳定窗口和缩容排空，避免反复抖动或中断正在执行的任务。

如果任务平均需 2 秒，单 worker 并发 10，理想吞吐约每秒 5 个；实际还需压测。用到达率和完成率规划容量，再校验内存、连接与外部限流，避免只按任务数量线性扩容。

### Q4. 新版本上线后一个区域错误率上升，怎么处理？

数据库变更是否也能直接回滚？

**答案：**

先按区域、版本和接口比较错误率、延迟与发布前基线，暂停继续发布。如果确认与新版本相关，就把该区域流量切回旧版本或回滚；灰度时设定可以自动停止的条件，但也避免噪声导致反复切换。

应用回滚不代表数据自动回滚。数据库变更要使用兼容的 expand-contract：先加新字段/结构，让新旧代码都能运行，再迁移，最后删除旧结构。不可逆业务写入需要单独修复，不能仅依靠重新部署旧代码。

回滚后还要验证错误率是否恢复、是否出现积压以及新版本产生的数据是否需要修复。告警解除不能只依据部署命令完成，必须观察用户路径和关键业务指标。

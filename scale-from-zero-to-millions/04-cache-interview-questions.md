## 相关公开反馈真题

### Google：设计分布式缓存 / Design a Distributed Cache

**标签：公开反馈真题（2025）。** [来源：候选人反馈汇总](https://www.reddit.com/r/leetcode/comments/1lvnd0t/)

**与本节的对应关系（学习映射）：** 直接相关，但完整题还需节点路由、复制和迁移；Redis Cluster 使用哈希槽，不能把所有缓存系统都说成一致性哈希。

**设计参考答案（非公司标准答案）：**

我先定义 get/set/delete、TTL、容量和一致性目标，确认缓存是否可丢失、是否要求读到最新值。通过客户端或代理按 key 路由到节点；实现可选一致性哈希或哈希槽，Redis Cluster 是后者，不能把两者当同一机制。节点保存 value、版本和到期信息，并按容量执行淘汰。

每个分区按需要配置副本，故障时切换并解释异步复制可能丢最近写入。扩容分批迁移分区，用版本化路由或重定向处理旧客户端。热点 key 单独用本地缓存、读副本或业务拆分缓解。cache-aside 场景还要控制 miss 回源和缓存更新竞态；缓存作为加速层并不自动提供业务数据库级耐久或强一致。

### Amazon：设计短链接服务 / Design a URL Shortener

**标签：公开反馈真题（2025）。** [来源：候选人反馈汇总](https://www.reddit.com/r/leetcode/comments/1lvnd0t/)

**与本节的对应关系（学习映射）：** 可练热门短链接缓存、miss 回源和缓存故障时的数据库保护。

**设计参考答案（非公司标准答案）：**

我先明确创建短链接和访问跳转两个核心功能，确认链接能否修改、是否过期、读写比例与峰值。API 提供创建与按短码跳转，数据库保存 code、target_url、owner、expires_at。短码可由唯一 ID 编码，或随机生成并通过唯一约束处理冲突；自定义别名同样需要原子占用。

跳转服务无状态化，先查缓存，miss 回源，验证过期或禁用状态后返回适当重定向。允许修改或需要可控统计时，避免不加分析地使用永久缓存的重定向。点击事件异步记录；读热点用缓存与副本，容量达到上限时按短码分片。刚创建后立即读取、链接删除与缓存失效都要定义一致性；故障时限流回源，不能假设 DB 能承担全部访问。

## 优先练习的面试追问

以下均为本节练习题，英文用于口述训练，不是公开面经逐字引文。每题保留速记要点，并附可口述的参考答案；方案需结合面试官给定的规模和约束调整。

### Q1. 给读多写少的服务加缓存，如何设计读写路径？

**英文口述：** Design caching for a read-heavy service.

**继续追问：** 缓存什么？key、TTL、容量和命中率如何确定？

**回答要点：** 以访问模式选缓存项。读先查缓存，miss 查询数据库并回填；写入需明确数据库提交与失效流程。依据热点工作集和陈旧容忍度选择容量、TTL。

**参考答案（可口述）：**

我会以数据库为权威存储，优先缓存重复读取多、计算或查询昂贵、允许短暂陈旧的数据。key 包含实体 ID 和必要的租户/版本信息，避免不同用户错误共用结果。

读路径是查缓存，hit 返回，miss 查询 DB 并回填；写路径先提交数据库，再可靠地失效相应缓存。TTL 根据更新频率和陈旧容忍度设置，容量按热点工作集估算，监控命中率、回源和尾延迟。对余额等必须准确的决策读，我会使用满足一致性要求的权威路径，而不是仅靠缩短 TTL。

### Q2. 先写数据库再删缓存，能保证一致吗？

**英文口述：** Can cache invalidation guarantee consistency?

**继续追问：** 读请求在写提交前拿到旧值，却在缓存删除后回填，会怎样？

**回答要点：** 画出并发时序：读 miss→读旧 DB；写提交→删缓存；读回填旧值。可按业务采用版本校验、可靠失效事件或关键路径直读权威存储；短 TTL 不等于强一致。

**参考答案（可口述）：**

不能保证。比如 A 缓存 miss 并从 DB 读到 v1；B 将 DB 更新为 v2 并删除缓存；A 随后把 v1 回填，缓存又出现旧值。另一个问题是 DB 提交成功但删缓存失败。

允许最终一致时，可以用可靠失效事件、重试和 TTL 控制陈旧风险；需要更严格的新鲜度时，应协调回填与失效，例如维护版本并拒绝过期回填，或者关键读绕过缓存。版本比较本身也要正确处理并发和缺失状态。延迟双删、短 TTL 都不能单独作为强一致保证。

### Q3. 热点 key 过期，大量请求同时 miss，怎么办？

**英文口述：** How would you prevent a cache stampede?

**继续追问：** 互斥锁失效或持有者崩溃怎么办？

**回答要点：** 请求合并或每 key 的回源协调、锁超时、异步提前刷新；允许旧值时可先返回旧数据。明确刷新失败行为，限制回源并发。

**参考答案（可口述）：**

我会让同一热点 key 的 miss 请求共享一次回源结果。一个请求负责加载，其余等待短时间；业务允许时也可返回旧值，由后台刷新，避免把所有请求同时压到 DB。

多实例协调需要考虑锁的有效期、持有者崩溃和晚返回的旧结果，不能让锁永远占用，也不能随意删除其他持有者的锁。提前刷新能减少过期瞬间的压力，但刷新失败时仍需有回源并发上限、短超时与降级。

### Q4. 请求大量不存在的 ID，如何避免每次访问数据库？

**英文口述：** How would you handle repeated cache misses for nonexistent keys?

**继续追问：** 空值缓存多久？新数据创建后如何刷新？

**回答要点：** 参数校验、短期负缓存或布隆过滤器。布隆过滤器可能误报；负缓存和过滤器更新需避免错误地长时间隐藏新记录。

**参考答案（可口述）：**

先校验格式与权限，拦截明显非法请求。合法但不存在的 ID 可以短期缓存“未找到”，避免每次重复查询；新记录创建时要清理负缓存或让其很快到期。

在数据集合适合维护的场景，可用布隆过滤器快速排除明确不存在的 key；“可能存在”仍需查缓存或 DB。误报只会多查一次，但过滤器更新落后可能让新记录被错误拒绝，所以新增数据与过滤器更新要设计好。还需要限流，防止攻击者不断换 ID 绕过负缓存。

### Q5. 大量 key 同时过期，或缓存整体不可用，怎么办？

**英文口述：** How would you survive a cache outage?

**继续追问：** 是否能让所有请求直接访问数据库？

**回答要点：** TTL 抖动处理集中到期；整体故障还需限流、并发上限、降级和渐进预热。不能假设数据库能承受全部回源。

**参考答案（可口述）：**

我会区分集中到期和整体故障。集中到期可以使用 TTL 抖动、分批刷新和热点预热；整体缓存故障时，先缩短缓存等待超时并触发降级，同时限制 DB 回源并发与请求速率。

例如正常 10 万读 QPS、99% 命中时 DB 大约接收 1000 次缓存 miss；缓存消失后，潜在回源可增长约百倍。DB 未必有这种余量，所以可以拒绝低优先级请求、允许返回旧值，并逐步恢复缓存。加副本和多级缓存有帮助，但必须验证故障域与容量，不能承诺任意故障都无影响。

### Q6. TTL 与 LRU/LFU 有什么区别？

**英文口述：** How do expiration and eviction differ?

**继续追问：** 热点变化快时如何选策略？

**回答要点：** TTL 决定数据有效期，淘汰策略决定内存紧张时移除哪些项。LRU 关注近期访问、LFU 关注频率；结合工作负载衡量命中率。

**参考答案（可口述）：**

TTL 是数据到期规则，LRU/LFU 是内存不足时的淘汰选择。未到 TTL 的项也可能被淘汰，已经到期的项不应再被当作正常有效缓存值返回。

热点随时间变化快时可评估 LRU，长期访问频率差异明显时可评估 LFU；一次性大扫描可能污染 LRU，因此要根据实际访问轨迹比较命中率。TTL 应由陈旧容忍度与刷新成本决定，不能因为选择了 LFU 就不考虑更新失效。

# 01. 单服务器架构与请求流程：面试题与答案

## 面试真题

### Amazon：设计短链接服务 / Design a URL Shortener

**答案：**

我先明确创建短链接和访问跳转两个核心功能，确认链接能否修改、是否过期、读写比例与峰值。API 提供创建与按短码跳转，数据库保存 code、target_url、owner、expires_at。短码可由唯一 ID 编码，或随机生成并通过唯一约束处理冲突；自定义别名同样需要原子占用。

跳转服务无状态化，先查缓存，miss 回源，验证过期或禁用状态后返回适当重定向。允许修改或需要可控统计时，避免不加分析地使用永久缓存的重定向。点击事件异步记录；读热点用缓存与副本，容量达到上限时按短码分片。刚创建后立即读取、链接删除与缓存失效都要定义一致性；故障时限流回源，不能假设 DB 能承担全部访问。

例如写入成功后缓存尚未填充，首次跳转应从能看到该记录的数据库读取。禁用链接若要求立即生效，不能只依赖长 TTL 的缓存；还要协调版本或权威校验。创建接口和跳转接口可独立扩容，因为两者负载通常差异很大。

## 本节练习题

### Q1. 用户输入网址到看到页面，中间发生了什么？

DNS 已缓存时有什么变化？加入 CDN 和负载均衡后请求如何走？

**答案：**

我会先区分首次访问和已有缓存、连接的访问。浏览器检查本地等 DNS 缓存，必要时通过解析器获得域名地址。首次 HTTPS 访问通常需要建立连接并完成 TLS 验证；HTTP/1.1、HTTP/2 常用 TCP，HTTP/3 使用 QUIC，已有连接可以复用。

浏览器发送带域名信息的 HTTP 请求；部署了 CDN 或 LB 时，请求先到相应入口，再按配置返回缓存内容或转发到应用。应用读取缓存或数据库后返回响应，浏览器解析 HTML、加载 CSS/JS/图片并渲染。DNS 负责解析地址，不负责转发 HTTP；加入 CDN 后也要区分静态内容和动态 API 的实际路径。

例如图片已经在 CDN，图片请求可能完全不访问应用和数据库；而用户资料 API 通常还需要应用处理。不能把所有资源画成同一条串行链路，也不能把“DNS 已缓存”解释成不需要发 HTTP 请求。

### Q2. 只有一台服务器的网站变慢，你先做什么？

怎样确定是 CPU、数据库 IO、带宽还是慢查询？

**答案：**

我先问“慢”的定义：哪个接口、什么时候、多少 QPS、读写比例、P95/P99 和错误率是否变化。随后看 CPU、内存、磁盘 IO、带宽、连接池及数据库慢查询，用请求链路耗时判断主要瓶颈。

如果慢查询占主导，先优化查询和索引；Web 与 DB 争抢资源时拆开；静态文件占带宽时用对象存储和 CDN；Web CPU 饱和时考虑无状态化后水平扩展。每次改变后比较相同负载下的延迟和资源使用，而不是一次性增加所有组件。

例如接口延迟 800 ms，其中数据库查询占 700 ms，加 Web Server 很可能没有明显收益；如果应用 CPU 已饱和而 DB 很空，扩 Web 才更合理。我会用分层延迟比较改变前后的效果。

### Q3. 把 Web 和数据库拆成两台机器后，系统是否高可用？

任意一台机器宕机分别影响什么？

**答案：**

不能。拆分让应用和数据库独立选择机器、部署和扩容，也减少资源争抢，但任何一台故障仍可能中断服务。

应用层需要多个实例和健康检查，数据库需要副本与可执行的切换机制，入口 LB 也要高可用。副本应跨合适的故障域，并留出故障后接管容量。网络和共享存储也可能成为依赖故障点，所以高可用要检查整条请求路径。

例如两台 Web 共用一台数据库，Web 节点故障可以切走，但数据库故障仍可能中断全部请求。读副本能保留查询能力，也不代表写服务会自动恢复，还需明确提升和切换步骤。

### Amazon：设计短链接服务 / Design a URL Shortener

**标签：公开反馈真题（2025）。** [来源：候选人反馈汇总](https://www.reddit.com/r/leetcode/comments/1lvnd0t/)

**与本节的对应关系（学习映射）：** 作为整章综合练习，串起读取缓存、持久化、复制、热点与扩容；补短码生成与冲突处理。

**设计参考答案（非公司标准答案）：**

我先明确创建短链接和访问跳转两个核心功能，确认链接能否修改、是否过期、读写比例与峰值。API 提供创建与按短码跳转，数据库保存 code、target_url、owner、expires_at。短码可由唯一 ID 编码，或随机生成并通过唯一约束处理冲突；自定义别名同样需要原子占用。

跳转服务无状态化，先查缓存，miss 回源，验证过期或禁用状态后返回适当重定向。允许修改或需要可控统计时，避免不加分析地使用永久缓存的重定向。点击事件异步记录；读热点用缓存与副本，容量达到上限时按短码分片。刚创建后立即读取、链接删除与缓存失效都要定义一致性；故障时限流回源，不能假设 DB 能承担全部访问。

### Meta：设计 LeetCode / Design LeetCode

**标签：公开反馈真题（2025）。** [来源：候选人反馈汇总](https://www.reddit.com/r/leetcode/comments/1lvnd0t/)

**与本节的对应关系（学习映射）：** 串起无状态 API、队列、worker、存储、监控和独立扩展；补判题沙箱。

**设计参考答案（非公司标准答案）：**

先确认题目浏览、提交判题、结果查询、比赛和排行榜的范围。API 保存 submission_id、用户、题目、代码引用、语言和状态，再可靠发布判题任务，返回 pending。worker 在隔离沙箱内编译运行，用 CPU、内存、时间和网络限制保护平台，测试数据也需受保护。

判题结果持久化后更新提交状态，同一 submission_id 的重复执行不能重复修改成绩。队列按语言或资源类型分组，扩容受沙箱启动和下游容量约束。比赛排名从可信结果与规则计算，缓存或增量更新读模型；监控等待时间、判题失败、热点比赛和重复消息。仅加入 MQ 不足以完成代码隔离与比赛正确性设计。

本节未核实到可独立归属某公司的逐字追问题目；上面的完整题只是本节知识的应用入口。

## 优先练习的面试追问

以下均为本节练习题，英文用于口述训练，不是公开面经逐字引文。每题保留速记要点，并附可口述的参考答案；方案需结合面试官给定的规模和约束调整。

### Q1. 单机网站如何逐步支持百万用户？

**英文口述：** How would you scale an application to millions of users?

**继续追问：** 每加一个组件，由哪个需求或瓶颈触发？

**回答要点：** 先澄清功能、DAU、每人请求数、读写比、峰值、延迟和可用性。按证据拆 DB、扩 Web、加缓存/CDN、异步处理、扩数据层，顺序由负载决定。

**参考答案（可口述）：**

我会先确认“百万用户”是注册还是日活，明确功能、读写比例、峰值 QPS、数据增长、P99 和可用性。比如假设 100 万 DAU、每人每天 20 次 API 请求，平均约 231 QPS；峰值若假设十倍则约 2310 QPS。这是示例估算，不是所有百万用户网站的负载。

随后按瓶颈演进：分离 Web/DB，Web 外置状态并通过 LB 扩容；重复读取加缓存，静态资源加 CDN；耗时任务异步化；数据库先优化和复制，再按需要分片。多区域由延迟和容灾目标驱动。每一步补监控、冗余和故障验证，避免按固定顺序堆组件。

### Q2. 百万用户是否一定需要分片、多区域和微服务？

**英文口述：** Does a million-user application need sharding and microservices?

**继续追问：** 如果只有少数用户每日活跃呢？

**回答要点：** 注册用户数不能直接决定 QPS。先估算并测量工作集、吞吐与存储；多区域由延迟和容灾目标驱动，服务拆分由独立扩展和团队边界驱动。

**参考答案（可口述）：**

不一定。100 万注册用户若只有 1 万 DAU，和 100 万 DAU 的系统负载完全不同；请求成本、读写比例与热点也会改变容量。先估算流量、存储、带宽和热点工作集，再用压测验证单区域方案。

分片是解决已确认的数据层上限，多区域解决地理延迟和故障目标，服务拆分解决业务边界、团队协作和独立扩展。它们增加复制、事务、路由和运维成本，只有需求能证明收益时才引入。

### Q3. 如何保证某一层故障不会拖垮整个系统？

**英文口述：** How would you remove single points of failure?

**继续追问：** Web、LB、缓存、DB、MQ 分别故障时是什么行为？

**回答要点：** 逐层说明冗余、检测、切换与容量；再说明超时、有限重试、限流和降级。多个副本若共享同一故障域仍可能一起失效。

**参考答案（可口述）：**

我逐层检查 LB、Web、缓存、数据库、队列和存储是否有冗余，副本是否跨故障域，检测和切换能否执行，以及故障后剩余容量是否足够。单个进程有副本不代表共享网络或机房故障也能承受。

然后保护依赖：调用有超时，重试有限且带退避，写入重试具备幂等，缓存失效限制回源，慢下游触发熔断或降级。监控要能发现故障和用户影响，并通过演练确认恢复行为；不能只在图中画多个方框就宣称高可用。

### Q4. 什么时候从单体拆成独立服务？

**英文口述：** When would you split a monolith into services?

**继续追问：** 会新增什么复杂度？

**回答要点：** 按业务边界、独立容量需求和开发部署需求拆分；考虑跨服务通信、事务一致性、数据所有权和运维成本，不能只因用户多就拆。

**参考答案（可口述）：**

当一个模块有清晰业务边界，需要独立容量、发布节奏或团队所有权时，我会考虑拆分。比如图片处理需要大量计算，可从主 Web 服务抽成独立 worker，先获取明确收益。

拆分前确定数据归属、接口和版本兼容，再处理跨服务失败、事务一致性、日志追踪和部署。若所有操作仍强耦合并共享数据库，过早拆分可能只增加网络调用；早期模块化单体也能保留将来拆分的边界。

### Q5. 如何验证架构能承受目标负载和故障？

**英文口述：** How would you validate scalability and availability?

**继续追问：** 只测正常情况下峰值 QPS 够吗？

**回答要点：** 用真实访问分布压测、测尾延迟和容量余量；模拟缓存故障、副本延迟、worker 崩溃与区域切换，验证恢复时间和数据正确性。

**参考答案（可口述）：**

先定义通过条件：目标吞吐下 P99、错误率、资源余量，以及故障后的 RTO/RPO。压测应模拟真实请求比例、热门 key、请求大小、冷缓存和突发，而不是均匀请求一个便宜接口。

再注入实例故障、缓存故障、复制延迟、worker 崩溃和区域切换，检查是否出现重复业务效果、错误读写或不可恢复积压。除了峰值吞吐，还要做持续负载观察内存和连接泄漏，并确认恢复后能清理积压。验证结果决定是否继续扩容或修改设计。

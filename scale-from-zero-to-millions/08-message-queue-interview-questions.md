# 08. 消息队列：面试题与答案

## 面试真题

### Meta：设计 LeetCode / Design LeetCode

**答案：**

先确认题目浏览、提交判题、结果查询、比赛和排行榜的范围。API 保存 submission_id、用户、题目、代码引用、语言和状态，再可靠发布判题任务，返回 pending。worker 在隔离沙箱内编译运行，用 CPU、内存、时间和网络限制保护平台，测试数据也需受保护。

判题结果持久化后更新提交状态，同一 submission_id 的重复执行不能重复修改成绩。队列按语言或资源类型分组，扩容受沙箱启动和下游容量约束。比赛排名从可信结果与规则计算，缓存或增量更新读模型；监控等待时间、判题失败、热点比赛和重复消息。仅加入 MQ 不足以完成代码隔离与比赛正确性设计。

比赛题目、测试数据和用户代码要分别设权限。超时、编译错误、答案错误与平台内部失败是不同结果，平台故障可以重试，用户代码错误通常直接返回。重复任务的完成状态使用条件更新，避免晚到结果覆盖已经确认的成绩。

[题目来源](https://www.reddit.com/r/leetcode/comments/1lvnd0t/)

### OpenAI：设计 Webhook 回调系统 / Design a Webhook Callback System

**答案：**

我保存订阅配置、目标地址和投递策略。业务事件可靠产生后，为每个订阅创建稳定 delivery_id，进入持久队列；worker 发出签名 HTTP 请求，记录响应和投递状态。配置每目标并发与速率，避免单个慢目标拖住所有客户。

网络超时和暂时性错误按退避重试，永久失败或超过期限进入死信；响应丢失可能导致已处理事件再投，所以接收方应按 event_id/delivery_id 幂等。若要求顺序，要按订阅或业务实体串行协调并解释失败阻塞。校验目标、限制可访问地址以防 SSRF，使用签名和时间戳验证来源及重放窗口；提供投递查询和受控重放。

HTTP 超时无法确认接收方是否已完成业务，所以发送方不能保证外部效果仅一次。提供稳定事件 ID、投递历史与重放接口，让接收方去重；对于严格顺序订阅，失败事件是否阻塞后续事件应由订阅策略决定。

[题目来源](https://www.reddit.com/r/leetcode/comments/1lvnd0t/)

## 本节练习题

### Q1. 上传照片后要压缩、审核、生成缩略图，如何设计？

什么时候返回成功？队列里放图片还是引用？

**答案：**

客户端先上传图片到对象存储，服务校验对象可用后持久化任务，并可靠地产生处理事件。接口返回 task_id 和 pending 状态，表示上传已接收，不代表审核或缩略图全部完成。队列传对象地址、任务 ID、版本和处理类型，避免携带大图片。

worker 拉取任务、更新执行状态，生成缩略图或审核结果并持久化，再确认消息。用户可轮询状态或接收通知。每一步要支持重试和幂等，失败任务有明确状态；压缩、审核等阶段可独立扩容，但发布图片必须满足业务要求的审核条件。

图片处理任务可使用 image_id + version + operation 作为幂等标识，输出到确定的版本路径。worker 重试时先检查已完成状态和输出，再继续缺失步骤，避免重复写坏结果或重复通知。

### Q2. worker 处理成功，在确认消息前崩溃，会怎样？

重复投递如何避免重复业务效果？

**答案：**

消息可能再次投递，因此我把 job_id 作为稳定幂等键。若业务效果是数据库更新，可在同一事务中检查或插入去重记录、完成业务更新并标记成功，最后确认消息；第二次收到时直接返回已完成结果。

如果业务效果在外部系统，如发送邮件或扣款，本地事务不能覆盖外部调用。应优先传递外部支持的幂等键，或者查询状态和对账；否则“调用成功但本地未记录”的窗口仍在。处理中标记还需租约与恢复策略，防止 worker 崩溃留下永久处理中。

对数据库效果，去重表可在 event_id 上建立唯一约束，并在同一事务中完成业务更新。多个 worker 同时处理时，只有一个提交有效效果；事务回滚后重试仍可以继续，不能先永久标记成功再做业务。

### Q3. 生产速度长期高于消费速度，如何处理？

只增加 worker 是否有效？

**答案：**

队列增长速度大约是生产速率减去有效消费速率，长期为正就一定会耗尽容量或超过等待目标。我先看消息年龄、分区热点、单任务耗时和下游饱和度，确认到底卡在哪里。

worker 计算不足时增加实例；数据库或外部服务限制时，先优化批处理与下游容量，不能盲目增加 worker。必要时对生产者限流或背压、拒绝低优先级任务、限制重试。还要规划积压恢复速度：消费能力只等于当前生产能力，旧积压不会消失。

例如每秒入队 1000 条、消费 800 条，每秒净增加 200 条。提高到 1000 条只能停止增长，必须高于 1000 条才能排空历史积压；消费者扩容还需预留恢复阶段的额外吞吐。

### Q4. 失败消息如何重试？

接收方恢复前，重试会不会放大故障？

**答案：**

先分类失败。网络超时、部分 5xx 或限流通常可以重试；格式错误和无效任务通常应直接记录失败。可重试任务使用指数退避加随机抖动，设置最大尝试次数或最长投递时间，避免故障期间形成重试洪峰。

达到阈值进入死信队列并告警，保留任务 ID、失败原因和次数，便于修复后有控制地重放。重放仍要使用原幂等键，不能生成新 ID 导致重复效果。队列中的失败状态、客户端查询状态也要一致，不能悄悄丢弃任务。

例如目标接口返回 429 时应考虑其 Retry-After 信息，网络超时则可能已经处理成功。每次重试都沿用稳定投递 ID，并限制总并发；不能因为失败就产生新的业务事件。

### Q5. 同一订单事件有顺序要求，如何并行处理？

增加消费者会不会破坏顺序？

**答案：**

我只保证同一订单的顺序，而不是所有订单全局排序。按 order_id 分区，同一订单进入同一有序日志或消息组；不同分区可并行处理，分区内处理不能让后续事件越过尚未完成的前序事件。

事件携带实体版本或序号，消费者用条件更新检测重复与缺口。增加 worker 不会无限提升一个热门订单的处理能力；失败重试若被移到独立队列，也可能破坏顺序，需要决定阻塞、缓冲还是业务补偿。

例如订单版本依次为 4、5、6，消费者收到 6 而当前只有 4 时，不应直接覆盖。可以暂存并补取缺失事件，或查询权威状态重建；是否跳过旧事件必须由业务状态机明确允许。

### Q6. 数据库写成功但发消息失败，怎么办？

重试发消息会不会重复？

**答案：**

我不会在业务事务提交后仅做一次发消息，因为进程可能在两步之间崩溃。采用 transactional outbox：订单变更和待发布事件写入同一个数据库事务，事务失败两者一起回滚；提交后 relay 扫描 outbox 或通过 CDC 读取，并发布到队列。

relay 发布成功后再标记，若此时崩溃，事件可能重复发，但不会因仅一次调用失败而永久漏发，所以消费者仍需幂等。还要监控 outbox 积压、处理失败和保留时间。[AWS 官方参考](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)。

outbox 发布者不能在收到队列成功确认前删除事件。发布后但标记前崩溃时允许重复；同时要清理已发布记录并监控滞留，避免 outbox 随时间无限增长。

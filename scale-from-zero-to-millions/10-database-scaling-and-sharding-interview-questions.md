# 10. 数据库扩展与分片：面试题与答案

## 面试真题

### Google：设计分布式缓存 / Design a Distributed Cache

**答案：**

我先定义 get/set/delete、TTL、容量和一致性目标，确认缓存是否可丢失、是否要求读到最新值。通过客户端或代理按 key 路由到节点；实现可选一致性哈希或哈希槽，Redis Cluster 是后者，不能把两者当同一机制。节点保存 value、版本和到期信息，并按容量执行淘汰。

每个分区按需要配置副本，故障时切换并解释异步复制可能丢最近写入。扩容分批迁移分区，用版本化路由或重定向处理旧客户端。热点 key 单独用本地缓存、读副本或业务拆分缓解。cache-aside 场景还要控制 miss 回源和缓存更新竞态；缓存作为加速层并不自动提供业务数据库级耐久或强一致。

扩容迁移期间，旧客户端可能仍访问原节点，需要重定向或兼容路由。迁移不能把旧副本覆盖新写入，应使用明确的版本与写权威。若应用原先把缓存当唯一存储，就必须另外讨论耐久目标，不能套用“丢了直接回源”的假设。

[题目来源](https://www.reddit.com/r/leetcode/comments/1lvnd0t/)

### Amazon：设计短链接服务 / Design a URL Shortener

**答案：**

我先明确创建短链接和访问跳转两个核心功能，确认链接能否修改、是否过期、读写比例与峰值。API 提供创建与按短码跳转，数据库保存 code、target_url、owner、expires_at。短码可由唯一 ID 编码，或随机生成并通过唯一约束处理冲突；自定义别名同样需要原子占用。

跳转服务无状态化，先查缓存，miss 回源，验证过期或禁用状态后返回适当重定向。允许修改或需要可控统计时，避免不加分析地使用永久缓存的重定向。点击事件异步记录；读热点用缓存与副本，容量达到上限时按短码分片。刚创建后立即读取、链接删除与缓存失效都要定义一致性；故障时限流回源，不能假设 DB 能承担全部访问。

例如写入成功后缓存尚未填充，首次跳转应从能看到该记录的数据库读取。禁用链接若要求立即生效，不能只依赖长 TTL 的缓存；还要协调版本或权威校验。创建接口和跳转接口可独立扩容，因为两者负载通常差异很大。

[题目来源](https://www.reddit.com/r/leetcode/comments/1lvnd0t/)

## 本节练习题

### Q1. 复制和缓存都用了，数据库仍不够，怎么办？

瓶颈是容量、写吞吐还是慢查询？

**答案：**

我先区分存储不足、持续写吞吐不足、锁竞争和慢查询。查询与索引问题先修复，热点先单独处理；缓存和副本主要帮助读取，不能自动解除所有写瓶颈。

若确实到达单机存储或写入上限，我考虑分片，将不同 key 的数据和写入分给不同节点。实施前要确定分片键、路由、跨片查询与事务处理方式，并评估迁移成本。若业务允许且单机仍有空间，升级机器也可能是较简单的阶段方案。

例如只有一张索引不合适的表拖慢查询，分片会把同一个低效查询复制到多个节点。只有证明优化后仍无法满足容量目标，才值得引入路由、迁移和跨片协调的复杂度。

### Q2. 用户和订单按什么 key 分片？

按 user_id 分片后，按 order_id 查询怎么办？

**答案：**

如果主要查询是“用户的所有订单”，可按 user_id 共置用户相关数据与订单，减少跨片读取。但单个大用户可能产生热点，必须确认访问与数据分布。

若还要通过 order_id 直接查询，可让 ID 携带可解析路由信息，或维护 order_id 到 shard/user_id 的索引。索引与订单写入要协调，或明确索引异步更新期间的行为。全站报表可走独立分析读模型，避免每次在线查询广播所有 shard。

对于大租户，单纯按租户 ID 分片会让一个租户超过单片容量。可以在租户内部再按实体分片，但要说明该租户的列表查询如何聚合，以及新路由如何让客户端定位。

### Q3. user_id % 4 扩成 % 5，如何在线迁移？

迁移期间新写入落哪里？如何回滚？

**答案：**

直接将模数从 4 改成 5，会让大量记录改变归属，旧路由会读不到数据。我会先引入稳定的逻辑分片和版本化路由映射，将少数逻辑片从旧节点迁到新节点。

迁移过程保持明确的写权威：先回填历史数据，再捕获增量并校验；切换时可短暂暂停目标片写入以追平，或者使用能正确转发在途写的迁移协议。最后更新路由并保留旧副本用于验证。回滚必须能拿回新节点上的增量，不能只改回路由丢掉迁移后的写入。

验证应比较记录数量、校验和与抽样业务查询，并检查增量日志是否追平。路由发布也要有版本，让旧请求能够转发或重试，避免一部分应用仍读旧片、另一部分已经写新片。

### Q4. 数据条数均匀，为什么一个 shard 特别热？

一致性哈希能解决单个热门 key 吗？

**答案：**

相同条数的数据可能有完全不同的访问热度。一个名人账号或热门链接就能集中大部分 QPS，所以要比较每片请求量、每 key 负载和读写分布，而不只看容量。

读热点可用本地缓存、共享缓存和读副本分担；写热点可按业务拆成子 key 再聚合，例如计数分桶，但这会影响读成本和一致性。将热点单独放一片可隔离其他用户，但不自动消除单 key 上限；一致性哈希主要帮助重新分配节点，也不能直接解决这个问题。

对严格要求最新值的读，随意增加陈旧缓存副本可能违反需求；对写热点，分桶也可能失去单行原子语义。因此先确认是否允许近似、聚合延迟或局部顺序，再选择拆分办法。

### Q5. 分片之后如何 join？

反范式化后冗余字段如何保持一致？

**答案：**

优先让经常一起访问的数据共置在同一片。无法共置时，可以由应用分别查询再聚合，但跨片查询的网络开销和失败处理会增加；高频读取可建立冗余读模型，换取查询简单。

我会定义冗余字段的语义。例如订单中的购买时商品名是历史快照，不应随商品更名改变；若展示的是当前用户昵称，则可用事件更新读模型，带版本防止乱序覆盖，并用对账修复漏更新。反范式化省掉 join，但把复杂度转移到了写入、传播与修复。

例如订单列表冗余当前用户昵称时，用户改名后通过版本化事件更新；旧事件到达不能覆盖新昵称。若要求改名后所有订单立刻展示新值，则异步冗余读模型可能不符合要求，应重新选择查询路径。

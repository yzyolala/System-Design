# 07. 多数据中心：面试题与答案

## 面试真题

### Google：设计全球 IP 封禁系统 / Design a Global IP Address Blocking System

**答案：**

先确认规则来源、IP/网段形式、允许的全球生效延迟，以及哪些地域适用。我用控制平面校验规则，生成带单调版本的快照与增量，通过可靠通道分发到各区域。数据平面在请求入口本地查询适合 IP 前缀的结构，避免每次请求跨区查数据库。

节点原子替换已验证的规则集，报告应用版本；增量有缺口时重取快照。区域断网时按业务定义继续用最后有效版本或限制服务，并告警陈旧时间。添加和撤销都要传播，使用版本避免旧规则覆盖新规则。监控各区域生效进度和判定延迟；业务对规则新鲜度的要求决定故障时可用性取舍。

规则版本用于检测遗漏和回滚，节点应报告已生效而不只是已接收。添加与撤销都需要可靠传播；撤销后的旧版本不能再次覆盖新规则。控制平面故障不必立即停止所有请求，但必须监控各地规则陈旧程度。

## 本节练习题

### Q1. 单区域服务如何支持远距离用户？

只加 CDN 能解决动态请求延迟吗？

**答案：**

我先测网络距离在总耗时中的比例。静态内容通过就近 CDN 分发；动态请求如果仍受跨洋往返影响，可把应用部署到用户所在区域，并由全局路由引导流量。

多区域应用不一定自动降低延迟：若每次都跨区访问主数据库，仍会有远程等待。因此要确定数据归属，可能让用户写入 home region、在附近区域读允许陈旧的数据。是否跨区复制以及同步程度，由一致性、延迟和容灾目标决定。

例如欧洲用户的静态图片已由当地 CDN 提供，但每次资料修改还要访问美国主库。若写入量不大，可以接受跨区写延迟；若低延迟写是硬要求，则必须重新讨论数据归属和复制方案。

### Q2. 美国东部区域故障，如何切到西部？

为什么 DNS 切换不是瞬间？西部是否有足够容量？

**答案：**

首先定义目标，例如允许丢失多少已提交数据、希望多久恢复。故障时先判断区域及其数据库、队列等依赖是否健康，隔离失效写入口；确认西部数据进度与接管容量，再提升需要的写节点并切换全局流量。

DNS 切换受缓存 TTL 影响，已有长连接也不会自动迁移，所以客户端需要连接超时与重连。西部还要预热缓存并分阶段接管，避免冷缓存导致过载。RTO 衡量恢复目标，RPO 衡量数据丢失目标；实际达成要通过切换演练验证。

我会把切换分成检测、数据就绪、流量转移和恢复四个阶段计时。演练时确认旧区域写权限真的被隔离，新的缓存和队列能接管，并记录实际数据差距，不能只检查 DNS 已改成功。

### Q3. 用户在东部写入，西部读取，如何保证新鲜度？

同步复制和异步复制各付出什么？

**答案：**

如果要求用户读到自己的写，我可以将其读写都路由到同一权威区域；跨到另一地区时，也可携带写入版本，只有目标副本应用到该版本才返回，否则等待、回权威区域或明确报错。

异步复制让本地写快，但跨区读可能落后，灾难时也可能丢最近写入。同步复制要明确等待的是落盘还是应用：只等远端持久化不代表它已经能读取新值。它会增加跨区延迟，并在网络故障时限制写可用性，所以必须按具体业务选择。

例如用户切换区域后携带最后写入版本，西部未达到该版本时返回明确的等待或回源结果。用户读取其他人的数据是否同样要求最新，是另一个需求，应避免为所有读付出相同协调成本。

### Q4. 两个区域同时修改同一数据，怎么办？

是否可以总是用最后写入获胜？

**答案：**

我会先问是否真的需要同一 key 多区域同时写。若不需要，按用户或实体指定写入区域，并用版本条件更新控制并发，故障切换时保证旧写者被隔离。

若必须多地写，则按业务定义冲突：可合并的计数可用相应 CRDT，文档可保留版本并人工或业务合并。简单最后写入获胜会覆盖另一份更新，且涉及时间比较；余额、库存等正确性规则不能随意用它解决。必须说明哪些冲突允许合并、哪些要拒绝或协调。

例如用户修改昵称可以保留冲突版本后提示选择；库存扣减则需要限制写者或协调操作，不能让两地各自扣到负数后用最后写入覆盖。冲突处理必须围绕业务不变量设计。

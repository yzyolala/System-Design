# 02. 数据库选择与扩展方式：面试题与答案

## 面试真题

### Amazon：设计短链接服务 / Design a URL Shortener

**答案：**

我先明确创建短链接和访问跳转两个核心功能，确认链接能否修改、是否过期、读写比例与峰值。API 提供创建与按短码跳转，数据库保存 code、target_url、owner、expires_at。短码可由唯一 ID 编码，或随机生成并通过唯一约束处理冲突；自定义别名同样需要原子占用。

跳转服务无状态化，先查缓存，miss 回源，验证过期或禁用状态后返回适当重定向。允许修改或需要可控统计时，避免不加分析地使用永久缓存的重定向。点击事件异步记录；读热点用缓存与副本，容量达到上限时按短码分片。刚创建后立即读取、链接删除与缓存失效都要定义一致性；故障时限流回源，不能假设 DB 能承担全部访问。

例如写入成功后缓存尚未填充，首次跳转应从能看到该记录的数据库读取。禁用链接若要求立即生效，不能只依赖长 TTL 的缓存；还要协调版本或权威校验。创建接口和跳转接口可独立扩容，因为两者负载通常差异很大。

### Meta：设计票务预订系统 / Design a Ticket Booking System

**答案：**

先确认指定座位或普通票、锁座时长和支付流程。可用座位展示可以缓存，但售卖决策走权威状态。指定座位用条件更新或事务把 available 改为 held，写入 hold_id 和到期时间；普通票用满足库存不为负的原子扣减。

支付关联稳定幂等键，成功回调在事务中验证锁座仍有效并将 held 改为 sold，重复回调不重复出票。过期释放通过状态与版本判断，避免清理任务释放已经售出的座位。支付成功但锁座失效需要明确退款或补偿。热门场次入口排队与限流保护数据库，事件异步驱动通知，但不能把缓存库存或消息队列当作防超卖的唯一保证。

锁座过期任务与支付回调可能并发，二者必须通过状态和版本条件竞争，只有合法转换成功。清理任务只释放仍 held 且已到期的座位；支付回调若发现锁座已失效，则进入明确补偿流程，不能再次抢占已卖给别人的座位。

[题目来源](https://www.reddit.com/r/leetcode/comments/1lvnd0t/)

## 本节练习题

### Q1. 用户资料和订单存储，如何选择 SQL 或 NoSQL？

订单需要事务，用户资料主要按 ID 读，你会用同一种数据库吗？

**答案：**

我先列出查询和事务。例如订单需要按用户查列表、按订单 ID 查详情，并可能原子修改订单与库存，我会优先评估关系型数据库，利用事务、索引和约束表达这些规则。用户资料若主要按 ID 精确读取，关系型或 key-value/document 数据库都可能合适。

随后比较数据量、峰值读写、索引需求、陈旧容忍度、团队运维成本。两类数据可以使用不同存储，但早期不一定值得引入多套系统。NoSQL 也可能支持事务与强一致读取，SQL 也可以水平扩展；必须针对具体产品与配置判断。

例如订单状态和库存需要一起提交时，要说明事务是否覆盖这些记录；若已分到不同库，则单库事务不够，需要重新设计业务边界或补偿流程。数据库选择和数据放置应一起考虑。

### Q2. 流量增加十倍，升级机器还是增加机器？

哪一层遇到上限？成本和迁移复杂度如何比较？

**答案：**

我先定位增长落在哪一层，并确认是否持续。若只是早期容量不足，升级机器改动小，可作为短期方案；但需要评估成本、硬件上限和故障恢复。

如果应用计算负载能分散，我会用多台无状态实例与 LB。数据库读压力可用查询优化、缓存和副本，写入或存储达到单机上限才评估分片。扩容目标应包含故障余量；“增加十倍流量”并不意味着每层都增加十倍机器。

例如 Web 层扩到五台后，数据库连接数也可能增加五倍，所以每实例连接池和全局连接上限要一起调整。扩容一个层级可能把瓶颈移到下一层，需要重新测量。

### Q3. 数据库查询慢，为什么不能直接换 NoSQL？

是否检查索引、执行计划、锁竞争、连接池和查询模式？

**答案：**

数据库慢可能来自缺索引、扫描大量记录、锁竞争、连接耗尽、磁盘瓶颈或热点。先用执行计划、慢查询日志和资源指标确认原因，修复后再衡量。

换 NoSQL 不会自动消除热点或过多往返，反而可能失去需要的 join、约束和事务能力，并带来数据迁移、校验与切换风险。只有主要访问模式与新存储明显匹配、现有方案确有上限时，才提出迁移，并说明兼容、回滚和验证过程。

例如按用户查询订单却没有 user_id 索引，换存储前应先修复访问路径。迁移若最终不可避免，则需要回填历史数据、同步增量、校验结果并分批切换，不能直接替换线上数据库。

# 03. 负载均衡与数据库复制：面试题与答案

## 面试真题

### Amazon：设计短链接服务 / Design a URL Shortener

**答案：**

我先明确创建短链接和访问跳转两个核心功能，确认链接能否修改、是否过期、读写比例与峰值。API 提供创建与按短码跳转，数据库保存 code、target_url、owner、expires_at。短码可由唯一 ID 编码，或随机生成并通过唯一约束处理冲突；自定义别名同样需要原子占用。

跳转服务无状态化，先查缓存，miss 回源，验证过期或禁用状态后返回适当重定向。允许修改或需要可控统计时，避免不加分析地使用永久缓存的重定向。点击事件异步记录；读热点用缓存与副本，容量达到上限时按短码分片。刚创建后立即读取、链接删除与缓存失效都要定义一致性；故障时限流回源，不能假设 DB 能承担全部访问。

例如写入成功后缓存尚未填充，首次跳转应从能看到该记录的数据库读取。禁用链接若要求立即生效，不能只依赖长 TTL 的缓存；还要协调版本或权威校验。创建接口和跳转接口可独立扩容，因为两者负载通常差异很大。

## 本节练习题

### Q1. 一台 Web Server 宕机，如何让请求继续成功？

健康检查如何做？LB 自己故障怎么办？

**答案：**

我部署多个可替代的 Web 实例，由高可用 LB 根据健康检查分流。实例失效后，LB 停止发送新请求，剩余实例承担负载；扩容和部署也通过注册、就绪检查与连接排空完成。

健康检查要反映能否处理请求，但不能让共享依赖短暂异常把所有实例一起摘除。故障时在途请求仍可能失败，所以客户端需要超时与有限重试；写操作用幂等键防止重复执行。剩余容量必须能承受故障后的峰值，否则仅有副本仍会过载。

例如正常需要两台实例的容量，可部署三台或更多并确认一台故障后仍满足峰值。写请求失败后是否执行过可能未知，客户端重试应沿用同一个操作 ID，由服务返回已有结果。

### Q2. 用户修改资料成功，刷新后却看到旧值，为什么？

需要最新数据的请求是否都能读副本？

**答案：**

在单主异步复制中，写提交在主库完成，但副本可能尚未应用更新；刷新如果读副本，就会看到旧值。我先确认是否还有浏览器、CDN 或应用缓存，因为旧值不一定只来自复制。

要求 read-your-writes 的关键请求可直接读当前主库，或让客户端携带写入版本/提交位置，目标副本追上后才返回；等待超时则回主库或明确失败。写后固定几秒读主库只是近似方案，无法覆盖异常复制延迟，也不能保证故障切换后最近写入仍存在。

例如资料版本从 10 更新到 11，写响应带上版本 11。客户端后续读取可要求至少版本 11，服务从满足条件的副本返回；若副本落后则等待或改读主库，不能用旧版本伪装成功。

### Q3. 主库宕机，如何切换？会不会丢数据？

旧主恢复怎么办？已成功返回的写入一定存在吗？

**答案：**

切换前先确认故障，并通过租约、仲裁或 fencing 隔离旧主的写权限，避免网络分区造成两台同时写。再选择复制进度符合要求的副本、提升为主库、更新路由，并让应用重新连接；旧主恢复后先重新同步，不能直接重新接受写入。

异步复制下，客户端已经收到成功的最近写入可能未到新主，因此存在数据丢失窗口。同步复制能缩小这一风险，但必须明确提交要等待哪些节点、确认的是落盘还是应用，以及它增加的延迟与不可用风险。我会用 RPO/RTO 定义允许丢失和恢复目标，并演练切换。

还要处理不确定的写入结果：切换前客户端超时，并不说明原主没有提交。应用应按业务幂等键查询或重试，并对可能丢失的记录对账，避免一次故障演变为重复订单或重复扣款。

### Q4. 增加读副本能解决写入瓶颈吗？

复制和分片有什么不同？

**答案：**

通常不能。单主复制仍由一个主库接受写入，副本也要接收并应用日志。它们能分担允许读副本的查询，提高冗余，并间接释放主库部分资源，但不能把主库的写入无限并行化。

真正的写瓶颈先排查索引维护、锁竞争、批处理和热点；若单机能力不足，可按合适的 key 分片，让不同数据写到不同主节点。分片后每片仍可复制，分别处理写容量和故障恢复。

例如写入频繁更新同一计数行，增加读副本几乎不改变该行的锁竞争。若业务允许，可以分桶写计数后汇总；如果操作要求严格串行，则不能简单用分片声称消除了正确性限制。
